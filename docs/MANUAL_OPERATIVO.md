# Manual operativo

## Trabajo habitual
Abrir [panel](https://correradar-andalucia.github.io/panel/) y [Actions](https://github.com/correradar-andalucia/correradar-andalucia.github.io/actions). El panel representa la última publicación correcta; no demuestra que el último intento haya funcionado. Si falla, consultar pasos y logs sin exponer secretos. No descargar fuentes vetadas para diagnosticar.

### Direcciones de capitales en Cruzando la Meta (26/11/2026)

La 40 Media Maratón de Córdoba 2026 aparecía en las primeras entradas del calendario de Cruzando la Meta, pero su ficha publica el lugar como `Salida: Avenida del Conde de Vallellano, Córdoba · Córdoba`, no como `Córdoba (Córdoba)`. El lector rechazaba el lugar por no coincidir con el patrón anterior; no era prueba de que faltase el evento en la fuente. La ficha de Córdoba se cotejó por separado con el organizador IMDECO en PR #92.

El parser incorpora un segundo patrón **solo** para una dirección que contenga municipio y provincia explícitos y ambos sean una **capital andaluza de igual nombre que la provincia**. Un barrio, recinto, provincia diferente o dirección sin el prefijo `Salida:` se descarta; se conservan el patrón anterior, los vetos y el máximo de 18 enlaces sin solicitudes adicionales. Es una mejora de cobertura de la fuente ya habilitada, no permiso para nuevas fuentes o scraping, y no acredita que el cronometraje publique todas las carreras. Contrastar las futuras ediciones con sus organizadores antes de cambiar fechas.

## Revisar avisos
- [RSS cuatro fuentes](https://github.com/correradar-andalucia/correradar-andalucia.github.io/issues?q=is%3Aissue+is%3Aopen+label%3Arss-pendiente) y [Global Tempo](https://github.com/correradar-andalucia/correradar-andalucia.github.io/issues?q=is%3Aissue+is%3Aopen+label%3Agt-pendiente).
- **Diagnóstico de cero alertas Global Tempo:** abrir [Actions del detector](https://github.com/correradar-andalucia/correradar-andalucia.github.io/actions/workflows/detectar-alertas-globaltempo.yml), localizar `Global Tempo: diagnóstico RSS` y seguir la [guía de contadores y límites](diagnostico-rss-globaltempo.md). Los registros contienen solo agregados, no URL secreta ni fichas. Cero entradas de Google Alerts, descartes de formato y duplicados históricos tienen causas diferentes; el detector no descubre modificaciones de fichas conocidas.
- Verificar mismo año/edición, fecha futura, municipio y provincia andaluces, carrera a pie, ausencia de cancelación o duplicación, distancias/horarios si constan. Usar organizador, administración o ficha de cronometraje pública; no consultar inscritos. Fecha del aviso no es fecha de carrera.
- Presentar resultados con enlace y pedir autorización editorial agrupada (si no consta ya autorización específica). Para las cuatro nuevas fuentes: crear/actualizar catálogo de fichas fechado y registrado en scripts/oficiales.py; PR y pruebas, verificar deduplicación. No basta marcar casillas.
- Para Global Tempo: el flujo gt-aprobar publica únicamente nombre y enlace en sección separada, con revisión y sus tres casillas; la carrera fechada requiere fuente independiente. No usar etiqueta GT para otros proveedores.
- Cerrar como publicada tras éxito de despliegue y comprobación de incorporación (o descartar tras verificación y autorización). Mantener etiqueta de origen para deduplicar. Si el JSON no es accesible, usar ejecución y evidencia del histórico y declarar el límite.
- Notificaciones de nuevas carreras: Issues tras despliegue, seguimiento Watch > Custom > Issues y email en GitHub. Un aviso de descubrimiento y uno de publicación no son lo mismo.

### Sufijos de inscripción en los títulos de FAA

En el calendario de la FAA, una misma carrera puede aparecer una vez con su nombre y otra con una nota final entre paréntesis: «(inscripciones cerradas)», «(dorsales agotados)», «(inscripciones agotadas)» o «(plazas agotadas)». Esa nota es un **dato de disponibilidad temporal**, no una prueba distinta. El lector conserva el título original para el cotejo de inscripciones y normaliza solo el **nombre deportivo** antes de deduplicar. El sistema fusiona únicamente cuando coinciden fecha, provincia, municipio, modalidad y distancias compatibles; **no** une pruebas de distinta distancia/modalidad ni inventa inscripciones actuales a partir de un título anterior. Si hubo una incidencia automática de carrera nueva por este motivo, conservarla como registro histórico y aclarar después del despliegue corregido.

## Cancelaciones y retiradas editoriales

Las decisiones explícitas del responsable en el CSV editorial tienen prioridad sobre las fuentes directas, los cotejos, la semilla y los respaldos temporales. Para retirar una **edición concreta**, añadir una fila con `Estado` = `Cancelada`, `Anulada` o `Retirada` (se admiten variantes masculinas), `Fecha`, `Nombre`, `Localidad`, `Provincia` y `Modalidad` completos, `Fuente` HTTPS verificable y `Verificado` con la fecha de comprobación. `Publicar` puede estar en «no»: el veto sigue siendo explícito. No convertir la ausencia de una carrera en una cancelación.

La exclusión exige coincidencia de fecha, localidad y provincia, modalidad y nombre de la prueba (con la normalización editorial usada en deduplicación); **no** se veta solo por el enlace o por un nombre parecido. Si el veto no indica distancia, cubre todas las distancias de esa edición; si la indica, conserva las otras distancias identificables. Una edición de otra fecha no se retira automáticamente: investigar una posible reprogramación y modificar expresamente la decisión si procede.

Una fila de cancelación incompleta detiene la compilación en vez de permitir una reaparición silenciosa. Si existe una aprobación editorial contradictoria para la misma edición, el build también se bloquea y exige resolver la contradicción en el CSV. Las candidatas y la última publicación se filtran **antes** de combinar o restaurar carreras, de modo que una caída de fuentes no puede reintroducir la edición vetada. La auditoría `data/auditoria_duplicados.json` recoge el número de vetos y exclusiones por origen, sin declarar carreras canceladas por mera ausencia. El veto afecta a nuevas publicaciones, no borra el histórico de GitHub.

## Detección de lecturas silenciosamente vacías

Tras captar datos de los lectores ya habilitados, el sistema contrasta **la salida sin fusionar de cada lector** con carreras futuras atribuidas a ese lector en la última publicación confirmada. Solo usa registros con fecha de consulta original de hasta siete días, procedencia de lectura directa y sin respaldo temporal ni aprobación editorial. Una fila antigua no se vuelve reciente por reutilizarla. Se conservan las restricciones legales, los límites de consulta y las decisiones editoriales.

- **Bloqueo de calidad:** una fuente figura como `leida` pero extrae cero carreras y consta un mínimo de tres carreras futuras recientes de ese lector en la referencia; o el número declarado de fichas contradice las realmente entregadas. El informe la marca como `lectura_sospechosa` y `control_calidad.json` bloquea la nueva publicación. La última web y su copia confirmada permanecen disponibles. Una coincidencia por otra fuente no oculta que este lector dejó de funcionar.
- **Aviso sin bloqueo:** caída parcial relevante con resultados todavía presentes; o un lector de fichas detectó al menos tres enlaces pero no logró extraer ninguna carrera sin antecedentes suficientes. No equivale automáticamente a un fallo: puede ser un calendario estacional o fichas antiguas. No se retiran carreras ni se inventan candidatas por el aviso.
- **Sin sospecha automática:** calendario vacío sin antecedentes suficientes, fechas ya pasadas, consultas anteriores a siete días, modo de prueba offline, fuente pausada, error HTTP informado o veto de acceso/detalle. Ninguno se transforma en fallo temporal recuperable por esta comprobación.

Las métricas mínimas se guardan en `data/estado_fuentes.json` y `data/control_calidad.json`, y el resumen de Actions muestra `SALUD DE CAPTACIÓN` cuando hay sospechas o avisos. Los lectores que siguen enlaces de fichas solo informan cuántos enlaces detectaron, sin descargar páginas adicionales. Ante un bloqueo: revisar nombres y recuentos en la ejecución de **Actualizar carreras y publicar web**, comprobar cambios de formato mediante las pruebas del parser con HTML sintético y, si procede, preparar una corrección en PR. No desactivar la fuente, alterar sus permisos, forzar el despliegue ni conservar la fecha de una carrera por mera ausencia. La notificación mediante una incidencia dedicada sigue siendo una mejora separada: un fallo de Actions no demuestra que se haya enviado correo.

### Diagnóstico del lector Cruzando la Meta (20/11/2026)

La ejecución [#44827418106](https://github.com/correradar-andalucia/correradar-andalucia.github.io/actions/runs/44827418106) identificó una anomalía no bloqueante: **18 enlaces de fichas y 0 carreras extraídas**, sin errores de detalle. La inspección puntual de fichas públicas mostró que la cabecera reúne fecha, hora y ubicación, mientras que la localidad figura separada bajo «Dónde». El parser anterior podía confundir el horario con el municipio y descartar la ficha. No se ha demostrado que todos los enlaces sean futuras carreras andaluzas aptas.

El diagnóstico revisado conserva exactamente el límite de 18 enlaces de Cruzando la Meta y el uso de `fetch_if_permitted` con robots, dominios y errores sin excepciones. No añade fuentes ni solicitudes. Los descartes de las fichas consultadas se agrupan en `estado_fuentes.json` bajo `fuentes.cruzandolameta_detalle`: `consultadas`, `aceptadas`, `descartadas`, `errores` y `motivos`, **sin HTML, títulos de carreras, URL de fichas ni datos personales**. Las causas distinguen fecha, deporte, ubicación insuficiente, recinto sin municipio, cancelación y otras validaciones. No confundir «descartada por falta de municipio» con cancelada.

La mejora extrae la localidad del campo aislado «Dónde» cuando incluye provincia andaluza. Si solo constan una plaza, un pabellón u otro recinto, se descarta salvo que el municipio esté escrito expresamente en ese campo (por ejemplo, entre paréntesis) o en el caso específico ya verificado «Pabellón de Atarfe», con Atarfe también en el título. Se admiten fichas antiguas con localidad en un nodo independiente, pero no las recomendaciones de otras carreras. Una fecha/hora de salida no valida el municipio. Las distancias de otras modalidades, como marcha senderista, no se atribuyen a la carrera: el lector conserva solo distancias explícitas en el nombre.

En la primera ejecución autorizada posterior a integrar, comprobar que los motivos de descarte cuadran con las fichas consultadas, que el contador de la fuente no supera los límites, que las carreras añadidas tienen fecha, municipio y provincia contrastables y que no aparecen carreras canceladas o duplicadas. Verificar además el control de calidad, la continuidad y los avisos como en cualquier publicación. Hasta entonces, el diagnóstico es **una propuesta técnica en PR**, no una corrección confirmada en producción.

### Incidencia #68: recinto confundido con municipio

Después de integrar el PR #67, el lector recuperó 3 fichas de 18 y GitHub Pages publicó 181 carreras, pero la ficha `II CXM LA CALZADA 2027` quedó con `Palacio de Deportes de Vícar` como `localidad`. Es un recinto y no una localidad válida. La solución preparada en una rama independiente añade `palacio` a los prefijos de recinto ambiguo del lector y bloquea explícitamente `Palacio de Deportes` en el control de calidad general. Si la fuente no documenta el municipio de forma independiente, **omitir la ficha** hasta que esté documentado; no inferir «Vícar» por aparecer en el nombre de la instalación.

Tras autorizar e integrar la corrección, revisar que la localidad incorrecta no vuelve a aparecer en el calendario publicado (tampoco por respaldo de continuidad), que no hay pérdida territorial injustificada, que la generación real pasa calidad y que la rama de continuidad y avisos finalizan correctamente. La retirada de la ficha errónea no significa cancelación de la carrera, y su aviso anterior debe conservarse como histórico; no cerrar la incidencia sin verificación editorial.

### Cotejo independiente: II CxM La Calzada 2027

Separar las ediciones: la prueba prevista el **15/11/2026** fue [cancelada por el Ayuntamiento de Vícar](https://www.vicar.es/eventos/ii-cxm-la-calzada/), mientras que [la ficha de inscripción específica para 2027](https://inscrik.com/evento/ii-cxm-la-calzada-2027/) publica una carrera el **07/02/2027** a las **09:30**, con trail **24,5 km** y minitrail **15 km**. El organizador es Ayuntamiento de Vícar; el mismo Ayuntamiento [documenta en información de la edición anterior](https://www.vicar.es/los-paisajes-mas-idilicos-y-sorprendentes-regresaran-con-la-ii-cxm-la-calzada-de-vicar/) que el Palacio de Deportes está en **Vícar (Almería)**. No usar los datos de fecha de 2026 para afirmar la celebración de 2027 ni conservar como actual un estado de inscripción puntual.

Una ficha de 2027 puede incorporarse mediante **cotejo editorial específico** en `data/fichas_oficiales_*`, añadido a la lista explícita `FILES` de `scripts/oficiales.py`, sin cambiar ni desactivar el parser conservador de Cruzando la Meta. Conservar solo las distancias competitivas de trail y minitrail; no tratar senderismo 18 km como carrera a pie competitiva. Después de aprobar el PR de la ficha, verificar CI, deduplicación, localidad **Vícar** en el JSON confirmado, cobertura, noindex y notificaciones; no corregir por inferencia la instalación como municipio. El aviso histórico #68 se puede aclarar mediante comentario, sin borrarlo, y solo cerrar después de verificar la reincorporación correcta.

## Continuidad de GitHub Pages

Los dos flujos de publicación usan el mismo calendario anterior. Primero descargan el JSON público de Pages, validan su estructura y, cuando hay un despliegue confirmado en el diario, comprueban que coincida su SHA-256. Así se detecta también una respuesta anterior de la CDN. Ante error HTTP, JSON corrupto, calendario vacío, esquema inválido o huella distinta, usan la copia confirmada del diario si supera las comprobaciones de estructura, procedencia e integridad. Si ambas referencias fallan, la ejecución se bloquea antes de la captación y la web anterior sigue publicada. El resumen de Actions indica el origen elegido y los descartes. Si falla calidad, el log de compilación indica las ausencias por fuente.

El diario vive en la rama pública `estado-correradar-continuidad`, en `estado.json`. Cada escritura reemplaza la punta con un commit independiente mediante `--force-with-lease` y exige que el SHA remoto siga siendo el leído. La rama mantiene una única versión alcanzable. GitHub puede conservar objetos antiguos durante su limpieza. Los artefactos de calendario de cada intento se guardan durante siete días.

- `pendiente` es una escritura provisional antes de solicitar la publicación. Contiene únicamente versión de esquema, commit del código, ejecución, intento, fecha UTC, ID del artefacto y SHA-256 esperado. El ID nativo de Pages se añade al recibirlo. Se valida la lista de campos y sus formatos. El JSON candidato permanece en el artefacto de Actions. El diario provisional excluye el calendario candidato, las URL de fuentes, los datos de incidencias y las credenciales.
- `confirmado` contiene los bytes comprobados del JSON de Pages, junto con la identidad del intento, el ID de Pages y el SHA-256. Se conserva sin caducidad de almacenamiento y sigue disponible después de la caducidad de los artefactos. Si existe una copia anterior, escribir un pendiente no la sustituye.

Ambos workflows comparten la exclusión de GitHub Actions durante la generación, el despliegue y los avisos. Se conserva el artefacto de `actions/upload-pages-artifact@v4` y el entorno `github-pages`. El script llama al POST de Pages con el ID del artefacto, `GITHUB_SHA`, el entorno y el token OIDC. Guarda el `id` que devuelve la API antes de consultar el estado con GET. `actions/deploy-pages@v4` solo expone públicamente `page_url` y no permite persistir ese ID antes de su espera interna. La llamada directa posibilita reconciliar un job interrumpido. [API oficial de Pages](https://docs.github.com/en/rest/pages/pages?apiVersion=2022-11-28#create-a-github-pages-deployment) · [Interfaz de deploy-pages v4](https://github.com/actions/deploy-pages/blob/v4/action.yml)

Pages puede devolver el mismo ID en ejecuciones distintas de un mismo `GITHUB_SHA`. Se conserva el SHA admitido por la API y se identifica el calendario por su ejecución, intento y huella. Tras `succeed`, el job descarga el JSON público sin credenciales, solicita omitir la caché y reintenta hasta tres minutos ante errores HTTP, JSON inválido o bytes distintos. Confirma la copia solo cuando coinciden los metadatos y el SHA-256 de los bytes servidos con el intento actual. Si se agota la espera, la última copia se conserva y siguen bloqueados los avisos y las nuevas publicaciones mientras el intento esté pendiente. La siguiente ejecución vuelve a verificarlo antes de compilar. Un resultado terminal con un ID compartido por la copia anterior se trata como incierto. [Incidencia de deploy-pages #383](https://github.com/actions/deploy-pages/issues/383)

Los avisos y el cierre de incidencias se ejecutan después de confirmar la copia. Con el historial de avisos se deduplican notificaciones. La rama operativa tampoco toma datos de `data/carreras.json` de `main`.

Se mantienen los límites de recuperación de carreras de siete días desde la consulta original y de distancias de 30 días cuando corresponde. Se conservan los vetos de acceso, las pausas por derechos, la procedencia y los criterios de identidad y calidad. La validación del archivo admite las fechas de carreras ya pasadas en una publicación anterior. Su uso en una nueva publicación queda sujeto a los controles de caducidad. `CORRERADAR_FETCH=0` sigue disponible para CI y pruebas locales.

### Inicialización y reintentos

1. Tras la integración autorizada, comprobar que Pages sirve un calendario válido. El primer flujo protegido lo usa como referencia y guarda su primera copia al confirmar el despliegue. Si Pages falla antes de ese primer éxito y todavía no existe una huella confirmada, dejar la publicación bloqueada hasta comprobar los bytes públicos.
2. Si se bloquea una generación, consultar el resumen y los logs en Actions. Ante un despliegue de estado incierto, comprobar el ID que se registró y dejar que Pages alcance un resultado definitivo. Si el diario registra un pendiente sin ID, aplicar el procedimiento extraordinario.
3. Para volver a generar una publicación, ejecutar un flujo nuevo desde `main` o **Re-run all jobs** si el código del flujo sigue vigente. Un reintento del job de despliegue aislado no reutiliza artefactos de una compilación anterior. Un reintento de avisos puede continuar si ese intento sigue siendo el último confirmado. GitHub puede reemplazar un workflow que esté todavía en cola. Si afecta a una aprobación GT, revisar su incidencia y volver a aplicar la etiqueta tras comprobar su estado editorial.

### Recuperación extraordinaria

1. Coordinar la intervención con el responsable y pausar los dos flujos de publicación. Asegurarse de que no quede un despliegue en curso. Registrar la punta con `git ls-remote --refs origin refs/heads/estado-correradar-continuidad`. Usar `sin-inicializar` como valor esperado si la rama aún no existe.
2. Identificar en Actions el último despliegue correcto, su intento y su ID nativo de Pages. Si hay un intento pendiente sin ID y se localiza el ID **de ese mismo intento**, desde el checkout de `main` ejecutar `python scripts/publicacion.py asociar --estado SHA_DEL_DIARIO --despliegue ID_PAGES`. El comando exige un resultado definitivo y, en caso de éxito, verifica que Pages sirva exactamente el calendario pendiente. Si la solicitud nunca se aceptó, verificarlo en Actions y en el historial de Pages. En ese caso, al restaurar una copia que Pages esté sirviendo se puede usar `--descartar-intento-sin-id`. Si no se puede vincular el ID o confirmar el resultado, mantener el bloqueo.
3. Si la copia falta o está dañada, obtener los bytes exactos del último despliegue probado. Usar el JSON en Pages si es accesible y coincide con la evidencia del despliegue, o el artefacto `calendario-publicacion-INTENTO` de la ejecución identificada. El flujo ordinario anterior a esta protección lo llamaba `calendario-para-avisos`. Antes de usar un artefacto, confirmar en Actions que el job de despliegue de ese intento tuvo éxito y comprobar el ID nativo de Pages en sus logs. Calcular `sha256sum carreras.json`. En un calendario etiquetado, tomar commit, ejecución, intento y fecha de `publicacion_continuidad`. Para el formato anterior, documentarlos a partir de Actions y del commit con el que se generó la web. El comando compara los bytes con el JSON público si el diario carece de una confirmación previa que vincule la misma identidad, ID de Pages y huella.
4. En un checkout de `main`, con acceso autorizado al repositorio y un `GH_TOKEN` habilitado para consultar Pages, usar este comando. El token de Git usado para `origin` debe poder escribir en la rama del diario.

   ```bash
   export GITHUB_REPOSITORY=correradar-andalucia/correradar-andalucia.github.io
   python scripts/publicacion.py recuperar carreras.json \
     --estado SHA_DEL_DIARIO --despliegue ID_PAGES --sha256 SHA256_DEL_JSON \
     --commit SHA_DEL_CODIGO --ejecucion ID_DE_EJECUCION --intento NUMERO_DE_INTENTO \
     --fecha 2026-11-20T12:00:00Z
   ```

5. Verificar que se guardó la copia y reanudar los flujos previa coordinación. Si no hay bytes verificables del último despliegue, dejar el flujo bloqueado. Si la API devuelve un resultado incierto o el intento pendiente perdió su identificador, puede ser necesario consultar al soporte de GitHub antes de continuar. La copia no constituye una restauración del sitio HTML completo.

### Verificación tras la integración

- Comprobar en un flujo ordinario autorizado que el token del job puede crear y actualizar la rama de continuidad con `--force-with-lease`. Confirmar la referencia elegida, el éxito del control de calidad y el mensaje `Copia confirmada de GitHub Pages` antes del job de avisos.
- Comparar el SHA-256 registrado con el JSON servido por Pages y con `sha256` de `confirmado` en `estado.json`. Comprobar que coinciden el commit, la ejecución y el intento. En la siguiente ejecución programada del mismo commit, verificar que la confirmación cambia a los bytes del nuevo intento aunque Pages devuelva el mismo ID.
- En la siguiente aprobación editorial GT autorizada, comprobar la misma secuencia y que la incidencia se marca publicada tras confirmar la copia. Ejecutar `python -m unittest discover -s tests -p 'test_publicacion.py' -v` para verificar caídas, corrupción, reintentos y la pérdida de seis carreras sin provocar fallos en producción.
